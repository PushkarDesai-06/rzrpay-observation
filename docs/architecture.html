Revenue Recovery Loop

A payment fails. The system detects it, diagnoses why, chooses a bounded intervention, validates that intervention against deterministic policy, executes it, confirms the outcome with the provider, and only then counts the money as recovered.

The closed loop

One failed payment, end to end

Eight stages, each one recorded before the next begins. The model appears at exactly one stage and produces exactly one structured decision per cycle — everything before it is deterministic assembly, everything after it is deterministic enforcement.

The central guarantee

The model cannot reach a payment provider

ApprovedAction has a private constructor. The only place it can be built is the final step of evaluate() inside the policy engine, and the executor accepts nothing else — it checks instanceof before touching a provider. The direct path from a model decision to an external call is not discouraged; it is absent.

The second edge matters as much as the missing one. The context handed to the model includes an advisory budget summary so it proposes something plausible — but the policy engine re-derives every counter from the database. A model that misreads that summary, or is told to ignore it, changes nothing about what executes.

Case lifecycle

Thirteen states, one way to reach recovered

Transitions come from a hard-coded table. transitionState() is the only writer of case state and runs every move past that table first, so an illegal transition throws rather than corrupting the record.

ACTION_EXECUTING → ANALYZING exists because a failed provider call is new evidence. Re-running a stale plan would ignore what just happened; the agent reconsiders instead.

Where the guarantees live

Enforced by construction, not by convention

Each of these is the kind of rule a comment can state and code can quietly violate. They are placed where violating them is impossible rather than merely discouraged.

One case per payment

Five redeliveries of the same failure open one case and report the amount at risk once. Duplicates are logged, not silently dropped.

UNIQUE(payment_id)

No card charged twice

The executor claims the action's idempotency key in the database before the external call, so a crash mid-call leaves evidence and a re-run calls nothing.

UNIQUE(idempotency_key)

Revenue cannot be fabricated

A row must be RECOVERED to carry an amount, and must carry an amount to be RECOVERED. Written in one place, after the provider confirms.

CHECK · OutcomeTracker

History is immutable

The database aborts any UPDATE or DELETE against the audit log, the transition log, and recorded decisions.

SQLite triggers

No invented actions

The decision schema is generated from the same constant the executor switches on, so the two cannot drift. Anything else is a validation failure.

No unbounded pursuit

Three retries, two reminders, one payment link, 24 hours between messages, a 72-hour window, then the case stops.

Every action row records which provider carried it out, and the interface shows it. Simulated outcomes are seeded and reproducible: the agent and the baseline face the same draws, so the comparison measures the decision rather than the luck.
